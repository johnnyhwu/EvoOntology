# 這個環境中的任務（流程由程式控制，你只負責探勘與提出證據）

你拿到：建構題（工作負載）、業務窗口提供的說明文件（資料環境中的文件）、程式自動產生的資料剖析。
你可以用 `sql_query` 對資料庫做唯讀查詢，用 `read_doc` 重讀文件。

請完成：
1. 找出建構題需要的分析概念、指標與維度；
2. **逐一驗證業務文件中可驗證的主張**（名詞定義、代碼對照、時間規則、金額單位…），並探索文件沒提到、但會影響分析正確性的資料事實
   （例如單位、重複紀錄、缺值、孤兒資料、不同表之間的對帳關係）。資料無法佐證的文件主張要如實記錄，不可直接採信；
3. 對每一項值得保留的發現，提出一筆「證據提案」。

## 證據提案格式

最後呼叫 `submit_evidence`，args 為：
```
{"evidence": [
  {"id": "ev_<短名稱>",
   "claim": "<這筆證據要支持的一句話主張>",
   "query": "<可重現的 SELECT>",              // 與 doc_quote 擇一
   "doc_quote": "<文件原文逐字摘錄>",          // 與 query 擇一；系統會檢查它真的出現在文件中
   "validation_method": "<怎麼驗證，例如 distinct 值檢查／對帳／換算影響量化>",
   "interpretation": "<你對結果的解讀；若資料無法佐證文件主張，在此明說>"}
 ]}
```
**重要**：你只提供查詢；系統會自己執行查詢並把「實際觀察到的結果」寫進證據，你不需要也不能填 result。
查詢必須回傳至少一列、且單次結果不要太大（用彙總）。查詢失敗或引文不在文件中的提案會被丟棄。

建議 15–30 筆證據，覆蓋建構題需要的每個概念與每個潛在陷阱。不要把題目的答案寫進證據：證據是「資料的性質」，不是「某題的答案」。
